Meta-System 3.7 — User Guide

What Meta-System is, how its parts fit together, and how to use it day to day.

About this guide

No official 3.7 guide exists yet. This one is adapted from the 3.0 guide, the one written for the original install, and keeps only what describes how the system works. Anything tied to the original owner's own projects, history, or accounts has been removed. A few 3.0 features depend on tools a new install won't have; where that matters, this guide says so.

What Meta-System is

Meta-System is a working environment where the tools built in it get used to build the next tools. It has three layers. It helps to keep them separate.

  • The practice. A set of Claude Code sessions with defined roles. An overseer session sits at the top level. It tracks, advises, and coordinates across everything. Each project gets its own session, working inside that project's folder under that project's own instructions. Rules that bind every session live in one top-level instruction file, CLAUDE.md, and reach every project automatically.
  • The knowledge core. A small database on your computer, devlog.db, run by a companion tool called devlog-engine. It is the official record: the work journal, decisions, findings, and the project list. Some familiar-looking text files, like DECISION-LOG.md, are generated from it rather than written by hand.
  • The working screen. A browser app that puts live terminals, Claude chats, session history, the journal, decisions, ideas, and project status on one screen, in a layout you arrange, instead of a pile of separate windows.

Two principles shape the rest:

  • Local means internal. Your data and tools run on your own computer, with no cloud dependency.
  • Documentation is part of the product. A decision that exists only in a chat's scrollback counts as a failure. That's why so much of this guide is about where things get written down.

What 3.7 is for

3.0 is the original install, built on and around its owner's own work. 3.7 is a second, separate line. Its direction was confirmed by the owner on 2026-09-24. In the owner's words:

The end goal of ms3.7 is to become a system for other purposes by using the best of what we been developing from the beginning with Meta-System.

It is meant to follow "the same philosophical functionality" as 3.0 without being tied to the owner's identity or backstory. The directions it is meant to serve are a version a stranger can install, a version that doesn't depend on one particular AI tool, a cloud-hosted version, and possibly others.

3.7 starts empty on purpose. No logs, decisions, or ideas are copied over from 3.0.

How improvements reach 3.7

Fixes are still made in 3.0 first. Before one is carried to 3.7, it has to pass one test:

Is this a fix to how the system works, or to how the owner's own system works?

Fixes to how the system works carry over: panes, sessions, restarting after a reboot, logging. Anything tied to the owner's identity, history, projects, or accounts stays in 3.0, or carries over only as a generic version.

The screen: panes and workspaces

Everything on screen is a pane. A terminal is a pane, a chat is a pane, and so is the decision log. You can have two terminals, or two decision-log views, side by side. Panes can be tiled, resized, and stacked as tabs however you like.

The screen has two regions:

  • The global area holds the overseer's chat. It stays put no matter which workspace you're in.
  • The workspace area holds everything else, and it changes when you switch workspaces.

A workspace is a whole saved layout: which panes are open and how they're arranged. You can keep several, for example one per project, and switch between them. Switching hides and restores. It doesn't close anything.

Your layout is saved on the computer running the system, not in the browser, so it survives a lost browser profile. More than one browser tab can have the app open at once, and they stay in sync.

Pane types

Terminal

A real, live terminal. Closing the pane or the browser tab only hides it. Whatever was running keeps going in the background. The End Session button at the top of the pane actually stops it. Use that when you mean to stop something, not just put it away.

Each terminal pane remembers how to pick up where it left off. If a Claude session was running in it, it remembers that conversation. Otherwise it remembers which folder you were in. After a reboot, the pane reopens and resumes on its own.

Chat and personas

A real Claude Code conversation in a pane. Its history reloads when you come back to it, and it also appears in the Sessions pane like any other session.

The global chat is the overseer. Other chat panes come from the ＋ persona menu. A persona is a short instruction file that gives a chat a particular stance or job. Each persona is a file in the app's personas folder, and adding a file there adds a persona to the menu.

Limitation

Chat panes can edit files, but they can't run commands. Any action that needs your approval is quietly refused, because the chat pane has no approve or deny button yet. For work that needs to run commands, open a Terminal pane and start claude there.

Sessions

Two tabs. Live lists every Claude Code session running on the computer right now. Past lets you browse and search earlier ones. Both can show a whole conversation, and both have a Resume button that reopens the session in a new terminal pane. Plain terminals with no Claude in them don't appear here.

Watch and Settings

Watch runs health checks when you open it. It also drives the sprawl guard, a banner that lists sessions that have sat idle for a while (20 minutes by default) along with unsaved changes, so forgotten work doesn't pile up. Settings is where you adjust the guard.

Review, Notes, and Projects

Review is the work journal. You can browse and search it, and add an entry. Notes shows saved findings and is read-only. Projects shows each tracked project and its current state. On a fresh install these start empty.

Decision Log and Idea Bank

These are covered in their own section below.

Writing Style

Point it at a folder of your own writing, and it produces a single document describing your voice and style. Unlike every other pane, this one makes a real paid call to Claude and can take a minute or more.

Browser

A simple built-in web view for local pages. It has no back or forward buttons, it can't open files straight from disk, and sites that refuse to be embedded show up blank.

Who am I talking to?

Inside the app it's easy to assume every pane is the same assistant. They aren't. Claude Code decides who a session is from the CLAUDE.md instruction files in the folder it starts in, plus every folder above that one.

Where the session runsWho it is
The global chatThe overseer
A persona chatWhichever persona you picked
A terminal at the top-level folderThe overseer, from the top-level CLAUDE.md
A terminal inside a project's folderThat project's own session, still bound by the top-level rules

A rule of thumb: questions that cut across projects go to the overseer, and a project's own build decisions go to that project's session. If you're not sure who you have, ask it. "What are you, and which pane are you running in?" is a normal, useful question.

The decision log and the idea bank

Decision log

Each decision is recorded with its reasoning, what it assumes, what outcome is expected, and when to check back on it. Later, a Results line records how it actually turned out. Record a decision when it's made, not afterwards from memory.

In the Decision Log pane, + New and Edit write to the database, and the database then regenerates DECISION-LOG.md. Don't edit that file by hand. If someone does, the next save still lands in the database, but the file isn't overwritten. The pane shows a warning instead of silently discarding your edit, and a recovery command brings the hand edit back in.

Idea bank

A place to catch ideas that arrive at the wrong moment. Adding one should take almost no effort, and any session may add one without asking. The + Add button adds a new numbered entry to IDEA-LOG.md.

The idea bank is add-only. There's no edit button, by design. To refine an idea, add a new entry that replaces the old one. The history stays intact.

Starting, stopping, and reboots

The app runs as a small server on the same computer, and you open it in a browser there. It only accepts connections from that computer. Opening it requires a private link that includes a secret access code. Keep that link to yourself. It stays the same across restarts, so a bookmark keeps working.

It starts itself when the computer boots. After a reboot or a crash, the server comes back on its own and reloads your last layout. There are also start and stop scripts in the app's folder if you ever need to control it by hand. Stopping the server doesn't stop what's running in your terminals.

The rules every session follows

The top-level CLAUDE.md sets an authority contract that every session obeys, including every pane in the app. In short:

  • Free to do without asking: read, analyze, advise, and draft; add to the idea bank; record decisions; create or edit files you asked for in the current conversation.
  • Asks you first: any commit (saving work into version history); any file deletion; installs, configuration, and scheduled-task changes; changing anything you edited by hand; anything that leaves the computer; starting work beyond the step you asked for.
  • Verify before committing: actually run it or look at it, and confirm the result matches what was intended, not just that the change looks right.
  • Verify before claiming something is absent: no "that doesn't exist" or "that was never done" without first searching the full records, and showing what was searched and what was found.
  • Your word about your own history and intent is final. When you correct a fact about your own work, the session applies it. It doesn't argue from an old record.

Talking is the default. Before anything with real consequences, a session should check whether you want discussion, advice, a plan, or action.

Good habits

  • One session owns a problem. When something breaks, pick one session to handle it. Several sessions diagnosing the same thing without seeing each other does more damage than the original fault.
  • Know which session you're asking before you ask it to decide something.
  • Write decisions down when they're made.
  • Check before assuming something is lost. After a crash, data has usually survived. Look before concluding otherwise.
  • Close what you're done with. The sprawl guard will tell you what's idle, and End Session really stops a terminal.

Known limitations

  • Terminal scrollback doesn't survive a reboot. The sessions come back, but what was on screen doesn't.
  • A terminal pane can freeze without reconnecting. Reloading the page fixes it, and nothing running inside is lost.
  • Chat panes can't run commands, because they have no approval button yet.
  • Only one global, all-workspace pane is possible.
  • The Sessions pane shows Claude sessions only, not plain terminals.
  • The browser pane has no back or forward and can't open files straight from disk.
  • Some panes read from companion tools the original install has. On a new install they may show little or nothing.
  • The onboarding interview is not connected to 3.7 yet.

Installing

Not published here

Step-by-step install instructions exist, but they aren't published on this page. This section describes what an install consists of. It isn't a set of instructions to follow.

A working 3.7 install today is made of:

  • The Meta-System app (the meta-system-3-0 code), which is the browser screen and its server.
  • devlog-engine, with its devlog.db database, which is the knowledge core.
  • A baseline set of files: a top-level CLAUDE.md, a DECISION-LOG.md, and an idea bank.
  • The server set to start automatically when the computer boots.

It also needs Claude Code itself installed and signed in on the computer.
