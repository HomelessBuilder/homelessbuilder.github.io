The Onboarding Interview

How a new Meta-System install sets itself up: through a plain conversation, not a settings screen.

Read this first

The interview is now built into 3.7. You start it by choosing Setup from the persona menu. It has passed a full test on a practice install with a fictional user, but it has not yet run on a real install. The current status section at the bottom says exactly what is done, what has been tested, and what is still missing.

What it is

The onboarding interview is a conversation. The new user's own copy of Claude runs it the first time they use the system. There is no separate installer program: the interview is the installer. By the end of it, the system is set up around what they said.

To start it, open a workspace, choose Setup from the ＋ persona menu, and say hi. Setup is a chat persona whose only job is running this interview.

Claude already knows what a working Meta-System looks like, because it runs inside one. The person installing it doesn't need to know any of that. Their job is to talk about themselves and their work. Claude's job is to turn that into a finished, working setup.

Two paces

The interview opens by offering a choice, in roughly these words:

I can walk through this step by step, or if you'd rather just tell me about yourself and your work and let me handle the rest, that's fine too.

Step by step means more explanation and a longer conversation. "Tell me about yourself and I'll handle it" means less explanation and a shorter one.

The pace changes how much gets explained. It never changes who designs the system. Choosing the fast path does not hand the user any technical decisions, and the slow path doesn't either. That holds however technical the user is. The point isn't whether they could decide. The design already carries a lot of accumulated judgment, and making every new user work it out again from scratch is exactly the waste the system exists to avoid.

The four questions

All four are asked in plain language. None of them is a technical interview.

Question one

Who are you, and what do you do?

Your work, your goals, and what you'd want an assistant to already know so you don't have to repeat it every session. This becomes your profile, ABOUT-ME.md.

Question two

What's already in motion?

Your existing projects, work, and commitments. This tells Claude what the project list should already contain on day one. It is not asking whether to build the project list at all. That gets built either way.

Question three

What should I always check with you before doing?

Your hard boundaries, asked the way you'd ask a person, not the way you'd configure a system. Common answers are saving work permanently, deleting anything, or sending anything outside your computer, but it is whatever you name.

The system already comes with baseline working rules, and those are a floor. Your rules are added on top of them, never in place of them. If you ask for less checking than the baseline requires, the baseline rule stays, and Claude tells you so plainly.

Question four

How would you like this to feel day to day?

More explanation or less. More checking in or less. This sets how the system talks to you. It is not a menu of features.

There is no question about where the system should live. On 3.7 the install location is already fixed.

What you are never asked

The user never chooses the architecture. There are no questions about where data is stored, what format it's in, which modules to include, or any other implementation detail. Claude makes those calls itself, the same way it would for any other part of the build, without presenting them as choices you need an opinion on.

The check before building

Before writing anything, Claude summarizes what it is about to build and what it will contain. Then it waits for a plain go-ahead.

This is a courtesy check, not a design review. It confirms Claude understood you correctly. It isn't asking you to approve the architecture.

What it builds

A 3.7 install isn't blank. It already has a main instruction file with baseline working rules, a decision log, and an idea bank. The interview extends these files and never replaces them. After the go-ahead, it writes, for real:

  • Your profile, ABOUT-ME.md, from your answer to question one.
  • Additions to CLAUDE.md, the instruction page every Claude session reads first. Everything already in it is kept. It adds a pointer to your profile, your own rules below the baseline ones, a line on how you like to work, and your list of projects.
  • Your projects, in the project registry.
  • Your first decisions, in the decision log, for anything you settled in the conversation.
  • Your first ideas, in the idea bank, for anything you mentioned wanting to do later.

These are the same records the app's screens read, so what the interview writes shows up in the Projects, Decision Log, and Idea Bank panes.

It builds all of it even if you're unsure what you'll track. If you don't have clear answers yet, you get the complete system with empty, ready structures, not a smaller one. You don't have to know what you'll need before you have it. A system that starts out as almost nothing has nothing underneath it to improve.

If you open Setup again after it has already run, it tells you so, shows you your existing profile, and asks whether you want to update it or start over. It never overwrites your profile without a plain yes.

How it ends

The session ends with Claude telling you plainly what now exists, where it is, and what to do next. Usually that is simply to start talking to it about your work.

The design has one firm rule here. If Claude said it would build something, that thing must exist on disk before the session ends. A good conversation that never got written down doesn't count as an install.

Where the onboarding interview actually stands

Done

  • It is built into 3.7. A new Setup persona in the persona menu runs it.
  • It writes where the screens read: projects, the decision log, the idea bank, ABOUT-ME.md, and additions to CLAUDE.md.
  • It can record things. Chat panes still can't run commands in general, but the Setup persona is allowed to run the specific record-keeping commands the interview needs.
  • The baseline working rules are a floor. Your rules are added on top of them, never in place of them.
  • It extends the existing baseline files and never replaces them.
  • The "where should this live" question is gone, because the install location is fixed.
  • The original owner's name has been removed from its wording.

Tested, and how

It passed a full end-to-end test on a practice install with a fictional user. The test created projects, decisions, and an idea, and all of them could be read back afterwards. When the fictional user asked to drop one of the baseline checks, the baseline rule stayed. It has not yet run on a real install.

Still missing

  • Projects aren't linked to sessions yet. The projects it records appear in the Projects pane, but the sessions you work in aren't connected to them.
  • Nothing starts Setup automatically. You choose it from the persona menu yourself.
